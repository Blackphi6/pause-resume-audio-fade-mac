# ワイヤレスイヤホンでフェードインが弱い問題 — 調査と設計

- 状態: 調査完了。方式案を確定。**パラメータの値は実聴で決める**（下記「検証計画」）
- 対象: Mac 版 v2.3.0
- 症状: 有線イヤホンでは問題ないが、ワイヤレスイヤホンだと、再開時のフェードインがちゃんと掛かっておらず、効きが甘い

## 1. 結論

1. **アプリが出す音（デジタル）は、ワイヤレスでも有線と同じ正しいフェードインになっている。**
   再開直後の出力は 0.00 から始まり、約 256ms で全開（0.95）に達する。設計どおりの 300ms の余弦カーブ。
2. **Bluetooth の転送状態にも、再開時の異常は見つからなかった。**
   再開のたびに出力が止まったり、時間がずれたり、サンプルが途切れたりしていない。
3. したがって、効きが甘く聞こえる原因は、**アプリより後ろ（Mac の音声 HAL から先、イヤホン内）にある可能性が高い。**
   そこはソフトウェアからは観測できない。
4. そのため、「原因を特定してから直す」のではなく、
   **「ワイヤレスのときだけフェードインの形と長さを補正できる仕組み」を持たせ、実聴で値を決める**設計にする。
5. 有線（または内蔵スピーカー）で同じ測定を取る比較は、**まだ行っていない**（測定時はワイヤレスのみ接続）。
   差が出れば、原因の特定が進む。

## 2. 測定環境

| 項目 | 値 |
|---|---|
| 出力デバイス | AirPods Pro（Bluetooth 接続）、既定の出力・入力とも |
| サンプルレート | 48,000 Hz |
| IO バッファ | 512 フレーム（10.7ms） |
| デバイス遅延（OS が報告） | 7,680 フレーム（160ms）、ストリーム遅延 0、安全オフセット 0 |
| アプリの先読み遅延 | 100ms（標準） |
| 合計の遅延（目安） | 約 271ms（先読み 100 + IO 10.7 + デバイス 160） |
| 再生元 | `afplay`、別プロファイルの Chrome（`<audio>` の再生・一時停止）。振幅 0.03（−30dBFS） |

## 3. 測定結果

### 3.1 アプリの出力（デジタル）

| 項目 | 結果 |
|---|---|
| 再開直後の出力（Chrome 再生） | 0.00 → 0.95 まで約 256ms の余弦カーブ。再開 2 回とも同じ形 |
| 再開直後の出力（`afplay`） | 同じ形（有線で確認済みの E2E と一致） |

### 3.2 IOProc のタイミング

| 項目 | 結果 |
|---|---|
| 1 回あたりのフレーム数 | 常に 512 |
| 出力時刻 − 現在時刻 | 10.6〜10.7ms（一定） |
| サンプルの不連続 | 0 件 / 約 10,400 回（約 110 秒分） |
| 再開の前後での変化 | なし（遅延も連続性も変わらない） |

### 3.3 音の立ち上がりの速さ（−80dB → −45dB に達するまで）

| 再生元 | 立ち上がり |
|---|---|
| `afplay`（一時停止・再開） | 16 フレーム（0.33ms） |
| Chrome（`<audio>`、一時停止・再開） | 45〜63 フレーム（0.94〜1.31ms） |
| 合成音声（macOS の `say`、「三笘薫」） | 約 10ms（語尾は約 40ms） |

### 3.4 Bluetooth デバイスの状態（「実行中」を 10ms ごとに読んだ）

| 場面 | 結果 |
|---|---|
| アプリ起動直後（音なし） | 実行中 = 0。アプリが無音を出していても、デバイスは起動しない |
| 最初の音（再生開始） | 0 → 1。**デバイスの起動は、音がタップに届く約 220〜500ms 前** |
| 一時停止 5 / 12 / 20 / 30 / 60 / 120 秒のあとの再開 | **ずっと 1 のまま**。再開で冷たい起動は起きない |
| 10 分間の放置のあとの再開 | **ずっと 1 のまま** |
| 無音のあいだに −90 / −80dBFS のノイズを出力に混ぜる | 起動しない（実行中 = 0 のまま）。効果なし |

## 4. 仮説の検証

| 仮説 | 判定 | 根拠 |
|---|---|---|
| フェードインがデジタルで掛かっていない | **棄却** | 3.1。0.00 から全開まで滑らかに上がっている |
| IO のタイミングが乱れて、立ち上がりが欠ける | **棄却** | 3.2。不連続 0 件、遅延は一定 |
| 長い一時停止で Bluetooth が眠り、再開のたびに冷たい起動になる | **棄却**（10 分まで） | 3.4。放置しても実行中のまま |
| 通話中判定（v2.2.0）が、再生中に誤ってエンジンを止める | **棄却** | AirPods で音を鳴らしている間、エンジンは動作中のまま。マイク監視も反応しない |
| 滑らかな縁の判定（v2.3.0）が、動画の再開を「滑らか」と誤判定する | **棄却**（Chrome・`afplay` では） | 3.3。どちらも 2ms の窓より速く立ち上がり、「ぶつ切り」と判定された |
| ノイズを混ぜれば、デバイスが先に起動する | **棄却** | 3.4。−80dBFS でも起動しない |
| 音の転送より後ろ（イヤホン内の処理、コーデック）が効きを弱めている | **残る** | 観測できないが、他の仮説がすべて棄却された |

残る仮説の候補（いずれもイヤホンまたは OS の出力側で、アプリからは見えない）:
- 空間オーディオ（ステレオの空間化）による、立ち上がりのなまり
- 大きな音の低減、適応型の音量などの、イヤホン側のダイナミクス処理
- 最初の音のあとにだけ起きる、イヤホン側の立ち上がり処理

## 5. 設計

### 5.1 要件

1. ワイヤレス接続のときだけ、フェードインを補正できる。有線・内蔵スピーカーの動作は変えない。
2. 補正は自動で選ばれ、利用者が切り替えられる。
3. 補正の値（長さ・形）は、実聴で決められるよう、設定として持つ。
4. 補正をオフにすると、現在（v2.3.0）と完全に同じ波形になる。

### 5.2 方式: ワイヤレス補正プロファイル

**(a) 判定**
既定の出力デバイスの接続方式（`kAudioDevicePropertyTransportType`）が Bluetooth（`blue`）または Bluetooth LE のとき、
ワイヤレスとみなす。デバイスが変わるたびに判定し直す（出力デバイスの変更はすでに監視している）。

**(b) 補正の中身**
1. **長さ**: フェードインの長さを、標準の N 倍にする（候補: 1.5 倍 = 450ms）。
2. **形**: 余弦カーブを、指数 p で絞る。立ち上がりの初めが小さくなり、聴感上の「ゆっくり立ち上がる」感じが強まる。

```
x = 経過 / フェードイン長        （0 → 1）
基本 = 0.5 × (1 − cos(π × x))    （現在のカーブ。p = 1 のとき）
ゲイン = 基本 ^ p                 （p ≥ 1。終点は 1 のまま）
```

p = 1 は現在と同じ。p = 2 のとき、x = 0.5 で基本 = 0.5 → ゲイン 0.25（−12dB）になる。

**(c) 設定の持ち方**
- `FadeSettings` に `fadeInCurvePower`（既定 1.0）を追加する。1.0 のときは、今の計算式の結果と一致する（回帰テストで保証）。
- `Preferences` に「ワイヤレス補正」（自動 / 常にオン / オフ）と、「強さ」（弱 / 標準 / 強）を持たせる。
- 「ワイヤレスと判定された」ときだけ、強さに応じた（長さ, 指数）を `FadeSettings` に反映する。

**(d) メニュー**
- 「ワイヤレス時のフェードイン補正」: 自動（既定） / 常にオン / オフ
- 「補正の強さ」: 弱 / 標準 / 強

**(e) 強さのプリセット案（値は実聴で決める）**

| 強さ | 長さ | 指数 p | 狙い |
|---|---|---|---|
| 弱 | 450ms | 1.0 | 長さだけ延ばす |
| 標準 | 450ms | 1.5 | 長さと、立ち上がりの初めの抑えを足す |
| 強 | 600ms | 2.0 | 立ち上がりをかなり遅くする |

### 5.3 やらないこと

| 案 | 理由 |
|---|---|
| 無音のあいだに、極小のノイズを出力して、デバイスを起こしておく（キープアライブ） | 3.4 のとおり、効果がなかった。耳に届くノイズを増やすだけになる |
| 先読み遅延を、ワイヤレスのとき長くする | 音ズレが増える。ワイヤレスは、すでに約 160ms の遅延がある |
| 原因を決め打ちして、特定のイヤホンの設定（空間オーディオなど）を、アプリから変える | システム設定の変更になる。観測もできない |

### 5.4 併せて直す（ワイヤレス以外にも効く、小さな堅牢化）

滑らかな縁の判定（v2.3.0）の窓は 2ms で、Chrome の立ち上がり（最大 1.31ms）に対する余裕が約 1.5 倍しかない。
別の再生元で立ち上がりが 2ms を超えると、動画の再開でもフェードインが飛ぶ。
合成音声は約 10ms 以上かかるので、**窓を 4ms に広げても、合成音声の判定は変わらない**（Chrome との余裕は約 3 倍になる）。

### 5.5 既知の限界

- **アプリ起動直後、または AirPods の接続直後の最初の音だけ**は、デバイスの起動（音の約 220〜500ms 前）が絡む。
  ここは補正の対象外で、測定結果にとどめる。2 回目以降の再開には影響しない。
- 補正で効きが改善するかは、**実聴するまで分からない**。効かなければ、補正の既定は「オフ」のままにする。

## 6. 検証計画

### 6.1 自動で確認する

| 項目 | 内容 |
|---|---|
| 回帰 | `fadeInCurvePower = 1` のとき、出力が現在の波形とビット単位で一致する |
| 形 | p > 1 のとき、ゲインは単調に増え、終点で 1 になる。x = 0.5 での値が式どおり |
| 長さ | 長さを変えたとき、全開に達するまでの時間が設定値に一致する |
| 判定 | 接続方式が Bluetooth のときだけ補正が有効になる。有線・内蔵スピーカーでは、補正が自動のままでも無効 |
| 実機の出力 | ワイヤレス接続中に、プローブで再開直後の出力を測り、設定した形になっている |

### 6.2 耳で確認する（効果の判定はここ）

1. AirPods を接続し、YouTube などで、10 秒以上の一時停止のあと、再開する。
2. 補正オフ、弱、標準、強の順で、各 3 回ずつ聞き比べる。
3. 有線で聞いたときの再開の聞こえに、いちばん近いものを選ぶ。
4. 切り分けのため、次の設定もそれぞれ試す（1 つずつ切り替えて、補正オフのまま再開を聞く）。
   - 空間オーディオ: オフ
   - ノイズコントロール: オフ（適応型、ノイズキャンセリングをオフ）
   - 大きな音を抑える設定: オフ

**4 でどれかをオフにして聞こえが改善したなら、それが原因であり、アプリ側の補正は不要になる。**

### 6.3 受け入れ基準

1. 6.2 の聞き比べで、「有線と同等」と感じる設定が見つかる。
2. 有線・内蔵スピーカーでは、v2.3.0 と波形が同一（回帰テストと、E2E の出力で確認）。
3. 全テストが成功する。
